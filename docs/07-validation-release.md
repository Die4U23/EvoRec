# 验证、发布与恢复框架

## 1. 检查分层

| 层次 | 重点 | 当前状态 |
| --- | --- | --- |
| 输入契约 | 类型、范围、时区、批内重复、反馈语义 | M0 自动检查 |
| 服务边界 | 存活与就绪分离、真实能力、未实现接口 | M0 自动检查 |
| 业务逻辑 | 幂等、会话代数、过滤与状态转换 | M1-M2 待实现 |
| 数据库集成 | 唯一性、事务竞争、迁移与恢复 | M1-M2 待实现 |
| 模型与数据 | 切分、指标、产物兼容和推理 | R01–R06 离线实验已验证；R06 含全量重放与 50 项区间复算 |
| 前端与端到端 | 用户和运营场景 | M14、M24、M42 待实现 |
| 性能与发布 | 实际负载、版本切换、回滚 | O01、V01 待实现 |

输入校验测试保护已经定义的业务边界；后续优先增加跨层失败场景，而不是为每个简单函数机械添加测试。

## 2. 必须保留的失败场景

反馈事件重复与内容冲突；旧会话代数事件迟到；新品重复 ID；批次超出条数或体积；构建中断后重启；索引映射不一致；发布切换时并发推荐；模型回滚后下架仍生效；推理超时、排队超限与回退；实验结果缺失或版本不可定位。

每项场景记录输入、预期、实际结果和版本。处理失败必须能区分“未接收”“已接收未完成”“已完成但响应丢失”。

## 3. 发布清单

候选版本固定代码、依赖、数据库迁移、模型和索引。执行启动与健康检查、代表性业务场景、数据备份恢复、兼容性检查和回滚演练。单机展示允许明确的发布屏障，不宣称无停机高可用。

发布记录包括操作者、时间、旧新版本、检查结果、异常和恢复方式。正式展示前离线准备好数据及模型，确认资源、端口和启动步骤；外部下载不应成为现场正常操作的必需步骤。

## 4. 性能与研究验收

PRD 的 p95 ≤ 300 ms、20 请求每秒持续 10 分钟、有效请求成功率 ≥ 99%、100 条新品 60 秒内处理等都是目标。固定设备、模型、候选规模与请求分布后测量，包含队列和实际模型计算。达到或未达到都如实记录。

算法收益以统一协议的基线和消融证明。没有真实流量时完成离线评估与服务展示即可，不伪造 A/B 实验或业务增长。

## 5. 验证记录模板

每条记录使用“范围、环境、输入、方法、预期、实际、证据位置、限制、结论”九个字段。当前 M0 实测见 STATUS.md；未执行的数据库、Docker、前端和 GPU 验证不标通过。

## 6. 研究阶段的 GitHub 提交约定

从 2026-09-16 起，每阶段按协议登记、实现验证、结果交付分别形成真实 commit 并推送，核对远程提交号。训练记录实际代码 commit；每阶段只提交本次对应内容。原始数据、用户轨迹和模型留在忽略目录。未完成和失败的结果如实标注，不能用后补提交冒充历史开发过程。

有独立实现与结果交付的新研究使用 codex/ 前缀分支；每一部分提交并推送到同名远程分支。训练保存对应代码 commit，结果通过后再交付合并。未经验证不把进行中的结果写为 main 已完成。无关的用户文件不自动纳入提交。
