# EvoRec 实习指导评审与修订路线

日期：2026-09-16。目标：推荐算法实习，保留 C++ 工程优势。本文是对[原指导](../../EvoRec_推广搜实习方向指导.md)的评审与可执行修订；原文保留供对照，其中的操作建议不视为已执行事项。

**建议主线：围绕动态商品库中的冷启动，完成“定位瓶颈 → 改进召回 → 排序适配 → 统计复验 → 服务测量”的闭环。** 暂不同时扩展广告、搜索和生成式检索。项目的竞争力来自问题、方法和证据之间的联系；增加模型名字不能代替这条联系，也不能保证实习录用。

本轮完成事实复核、路线修订和仓库展示整理；没有训练 R06，也没有生成新的置信区间。

## 1. 原指导哪些建议可以保留

- 优先解决 GitHub 上缺失的研究成果，让公开仓库与本地实际完成状态一致。
- 同时展示整体表现、有历史请求表现和冷商品表现，解释分母。
- 保留 CF-blend 统计基线，也保留用于隔离排序作用的固定候选池 RRF。
- 冷商品候选覆盖不足已经有数据支持，应优先改善召回。
- 补冷加权模型的多种子复验、统计不确定性、可复现安装和最小服务演示。
- 把失败实验及其诊断写清楚，代码应便于阅读，正文应便于快速理解。

原指导中“面试必问”“远超一般学生”“一天实现”“必然数量级提升”等判断没有相应证据，修订路线不沿用这些保证。

## 2. 需要纠正的技术判断

| 原建议或判断 | 问题 | 修订 |
| --- | --- | --- |
| 把头条指标改成有历史分组 | R05 已按全部正反馈指标验证选轮，测试已查看；不能事后改写原实验主指标 | 全体指标与有历史分组并列，说明分组分析是补充；新实验的主次指标在运行前固定 |
| 以 CF-blend 替换 RRF 对照 | 两个对照回答不同问题；CF 输出自身 Top200，并非给完整并集候选评分 | 保留同评估协议的 CF-blend 链路对照，以及同候选池的 RRF 排序消融 |
| query 级 bootstrap 或 t 检验即可证明改进 | 同一用户有多个请求，不能默认独立；测试后挑选对比还会引入选择问题 | 优先用户聚类配对 bootstrap，固定比较集合，单列事后分析、多重比较与时间相关性限制 |
| SASRec 失败几乎肯定因为 1/20 采样导致短序列 | 当前按用户采样并保留入选用户的全部记录，不会直接截短这些用户的历史 | 先诊断原始序列分布、训练期有效历史、目标词表覆盖、实现和优化，再研究数据规模 |
| 把 denominator 改为 1 就能用全量用户 | 这会纳入旧留出用户；样本量、词表和共现统计也同时改变 | 新建训练用户清单，明确排除保留的评估用户；所有方法共同扩容，先做吞吐和内存试跑 |
| 5-core + leave-one-out + 全量排序即可和论文比较 | 数据版本、正反馈定义、切分、候选集合和负采样方式可能不同 | 区分参考实现复现与新协议实验；只有关键设定对齐才谈数值对齐 |
| 用评论记录做 CTR、校准、ESMM | 缺曝光分母、未点击样本和曝光→点击→转化链；商品 rating_number 不是用户事件标签 | 主线保留隐式兴趣排序。广告实验需另选拥有相应标签的数据，单独说明目标 |
| 添加 user ID embedding 是必需项 | R05 查询用户与 R03 训练用户隔离，训练用户 ID 查表对新用户无表示 | 先研究 item ID + 内容表示、显式 OOV 处理或候选感知历史聚合；不为技术名词改变协议 |
| 预训练编码器会带来数量级提升 | 当前还无实验；英文商品文本的编码模型、字段和截断都需验证 | 作为待检验假设，固定语言、模型版本和文本字段，报告无收益的结果也算完成 |
| 无历史用户加类别偏好入口 | 当前请求没有显式类别偏好，不能从待预测目标取类别 | 只使用请求时已知上下文；没有用户信号时只能研究非个性化分布，不称个性化提升 |
| 全局格式化不会影响审计 | 历史 source 快照虽保留，当前 R05 检查器还要求三个现有源码哈希与运行一致 | 单独做维护提交；保留旧快照验证并补新旧行为一致性检查，不能简单删掉哈希约束 |
| 按 R01→R05 补成开发历史 | 当前文件包含后续修改，提交日期也不是历史训练日期 | 按当前真实交付内容拆分提交，注明是补录；不改作者日期，不声称重建了每轮历史快照 |

数据语义依据：[Amazon Reviews 2023 官方字段说明](https://amazon-reviews-2023.github.io/)列出评论评分、评论时间和商品聚合评分数量；[ESMM 原论文](https://arxiv.org/abs/1804.07931)建模的是曝光、点击与转化的依赖关系。由这两者判断，当前数据不能验证真实 CTR/CVR 校准或 ESMM 的业务结论。

[SASRec 作者代码](https://github.com/kang205/SASRec/blob/master/util.py)采用每用户末次交互留出，评价代码抽取 100 个负样本。因此，本项目的全量合法商品评价不能直接与该采样评价数字横比。

## 3. 本次重新核对的数字

依据：R05 已完成运行、四个方法的逐请求轨迹与原始样本。运行摘要 SHA-256 为 ae8fcb98a5d26269529123c80ca924be02c553dbbb4b3f442d7d63f5e52dbab6。

| R05 方法 | 全部请求 NDCG@10，n=12,720 | 有历史 NDCG@10，n=5,214 | 冷目标 Top20 命中 / 7,088 |
| --- | ---: | ---: | ---: |
| CF-blend | 0.007188 | 0.005291 | 0 |
| RRF | 0.006537 | 0.003702 | 6 |
| ListMLP-s17 | 0.009426 | 0.010751 | 11 |
| ColdListMLP-s17（原验证规则所选） | 0.009119 | 0.010002 | 26 |

- ColdListMLP-s17 相对 CF-blend：全部请求 +26.86%，有历史请求 +89.03%；相对同候选池 RRF：全部请求 +39.50%。这些仍是离线观测差值。
- ListMLP-s17 相对 CF-blend：全部请求 +31.13%，有历史请求 +103.18%。原指导的 +104% 来自近似数字，不能当精确提升。
- 无正反馈历史的 7,506 个请求占 59.01%。本次复核的四个方法在这些请求上的推荐列表完全一致，NDCG@10=0.008506。“cold_user”指请求时无历史，不等同于训练未见用户。
- R05 样本共 136,953 名用户，100,463 名只有一条去重后交互，占 73.36%。这是该样本全时间段、全部评分的用户统计，不能直接当作 SASRec 训练期序列长度分布。
- 测试共 9,499 名用户，其中 1,656 名贡献多个正反馈请求，单用户最多 39 个。置信区间需要考虑用户内相关性。
- 合并候选池最多 400 件，实际平均 281.70 件；只有 127 / 7,088 个冷目标入池，入池率 1.79%。这个数是候选并集覆盖率，不能写成最终输出 Recall@200。
- 冷加权在入池冷目标中命中 26 / 127 ≈ 20.47%；全部冷目标命中率为 26 / 7,088 ≈ 0.37%。前者只能解释排序环节，不能代替后者。

RRF 对照仍然有价值：固定候选后比较可隔离排序器的作用。CF-blend 对照则检验完整推荐路径是否优于已有统计方法。两者同时报告，避免把整条链路差异归因于某一层。

复核入口：[脚本](../../scripts/check_internship_guidance.py)、[机器可读结果](../validation/internship-guidance-checks.json)、[R05 独立审计](../validation/ranker-checks.json)。新脚本重算保存指标的分组聚合并检查查询一致性；完整排名合法性由既有独立审计负责。本轮没有计算 bootstrap CI。

## 4. 接下来集中完成的研究主线

### P0：补齐交付和统计证据

先把现有 R01–R05 的代码、配置、图表和报告提交到仓库；数据、模型、原始逐请求记录和虚拟环境继续留在忽略目录。原始指导与修订版都保留，但 README 指向修订版。

接着固定冷加权配置，为 seed 29 / 43 复验；种子 17 的结果已经存在。保持 R05 的训练样例、编码器、候选池、学习率和验证选轮规则不变。旧测试已看过，因此这叫固定配置复验，不能包装成新的封闭测试。

置信区间的建议实现：

1. 从原始 CSV 按既有 query_id 规则恢复 user_id，并核对每个方法的一一对应关系；不公开用户 ID。
2. 每次抽样以用户为单位，同一用户的全部请求一同进入两个方法的比较。
3. 保留原指标的请求加权定义：重采样后用指标和除以请求数；不要无说明改成用户平均指标。
4. 固定随机种子和抽样次数（例如 10,000 次），报告绝对差值、区间、用户数、请求数、抽样单位和方法。逐种子区间与跨种子标准差分开。
5. 对全部请求、有历史分组和冷目标分组预先列明比较集合；区间跨零就如实报告。旧测试分析属于事后补充，不能据此回调模型。
6. 用户聚类处理不了所有跨用户商品与时间相关性；如做跨时段泛化主张，需另做时间区间敏感性分析。模型随机性与查询抽样不确定性也不是一回事。

**验收：** 冷加权三种子原始结果、检查点一致性和可复算的区间报告。没有提升也必须保留。

### P1：R06 多兴趣召回与排序适配

这一方向承接已观察到的候选覆盖瓶颈。当前内容路径把历史平均成一个向量；拟比较保留近期多个兴趣方向是否减少平均后的信息损失。它是一个简单、可解释的候选改进假设，暂不声称实现了 MIND 或 ComiRec。

拟比较：

| 实验 | 内容候选 | 排序器 | 用途 |
| --- | --- | --- | --- |
| A | 现有历史平均向量 | 固定 RRF / 冻结 ColdListMLP | 基准 |
| B | 平均向量与近期多兴趣列表合并 | 同一冻结 ColdListMLP | 测量召回变化及旧排序器的适应程度 |
| C | 与 B 相同 | 用新候选重新训练 ColdListMLP | 测量排序适配的附加收益 |

拟固定协同候选 200、内容候选 200、去重后总池至多 400；多兴趣来源在内容预算内合并，不能靠无上限扩池制造收益。相同候选数量不代表相同计算成本，应同时记录评分次数、耗时、显存和实际并集大小。

注册新留出用户桶，验证与 R01–R05 的用户交集为空，模型训练仍遵守时间边界。先冻结配置、质量门槛、选型与同分规则，再训练和验证；冻结方法后只进行最终测试。R06 当前尚未落地。

主要观察候选池覆盖率、冷目标入池率、整体与分组 NDCG@10、最终 Recall@20，以及池内排序转化情况。同时拆出有历史 / 无历史冷目标，避免把只有有历史用户受益解释成全人群改善。

**验收：** A/B/C 消融、相同数量预算、逐请求召回来源、三个种子、合法性审计、质量与成本权衡。新排序器和冻结模型使用不同阶段的验证数据时要明确说明，不能把端到端差值全部归因于召回。

### P2：更强内容表示与可扩展双塔

先做冻结文本编码器的低成本筛查，再决定是否训练：

- 固定一个适用于商品文本语言的编码器版本、许可证、输入字段、截断长度和归一化方式。首先与 TF-IDF/SVD 使用相同标题和类别；新增 description/features 另做字段消融。
- 记录静态元数据假设和预训练模型可能包含后期知识的限制，不把它称作严格历史内容可见性的证明。
- 比较冷 / 热商品候选覆盖及表示缺失率，再决定是否保留模型。没有提高就停下，不预设数量级收益。
- 双塔训练可比较全词表 CE、in-batch negatives 和采样校正版本。按训练采样机制估计 Q，显式处理重复商品、同一用户的已知正反馈和假负例；不同训练规模同时报告预算。
- log-Q 校正针对采样分布偏差，不能修复未记录的曝光偏差，也不是加一个公式就必然提高效果。[Google Research 原论文](https://research.google/pubs/sampling-bias-corrected-neural-modeling-for-large-corpus-item-recommendations/)提供方法依据。

**验收：** 字段、编码器和损失各自的消融，新的留出协议、实际资源预算与失败记录；不把多个因素同时改动的结果解释成单一组件收益。

### P3：序列模型诊断，作为有边界的并行研究问题

先核验，后扩容。不要以“必须打败 ItemCF”为验收标准。

诊断顺序：训练期正反馈长度分布 → 查询有效历史分布 → 测试目标是否在训练词表 → warm/cold、历史长度分组表现 → 小样本过拟合和掩码正确性 → 参考实现与损失差异 → 数据规模 / 优化超参消融。

现有神经实现是 SASRec-style、全词表 CE，不应默认等同于作者原始实现。现有 dropout 已有默认值，需区分“已有功能”和“尚未搜索的参数”。

扩数据时，固定保留的评估用户和时间边界；各方法使用同一训练集增量，记录有效样例、词表、耗时和峰值资源。增加其他用户可以改变商品覆盖和协同结构，并不保证单个用户的历史变长。8 GB 显存是否足够由试跑测量决定。

参考实验单独命名为标准协议对照，不占用已拟定的 R06 多兴趣编号。5-core 的数据筛选方式和使用未来交互形成的总体选择必须说明；不能拿其高分替代动态商品库的结果。

**验收：** 能排除哪些解释、支持哪些解释，以及尚不能区分的因素。负结果同样能够形成有说服力的研究故事。

### P4：最小服务与 C++ 差异化

先接入冻结 bundle，包含编码器、统计模型、排序器、商品版本、特征 schema 和指纹。实现单个推荐入口、合法性过滤、候选不足回退、超时、并发和就绪检查。现有 FastAPI 状态服务不是在线推荐服务。

先测精确向量检索；候选合法性过滤必须与离线一致。再用成熟 ANN 库做质量 / 延迟对照，报告过滤后的推荐效果、近邻重合率、建索引耗时、内存和更新代价。近邻召回率与真实目标 Recall@K 是两个指标。

如果剖析确认检索或特征处理是瓶颈，再用 C++ 优化其中一个环节。自行实现 HNSW 可作为独立学习项，首轮不要求同时承担算法正确性、跨语言绑定和动态索引工程。

压测固定硬件、索引大小、并发、预热、请求分布和运行时长，记录 p50/p95/p99、吞吐、错误率、排队及各阶段耗时。20 QPS / p95 ≤ 300 ms 是原目标，当前没有达标证据。

**验收：** 可运行请求样例、版本匹配检查、故障回退测试和可重复的压测报告；不把离线批量 GPU 吞吐写成线上延迟。

## 5. 暂缓或条件化的方向

| 方向 | 进入条件 |
| --- | --- |
| DIN / item ID + 内容精排 | 召回覆盖有改进，能用固定候选池检验表示与候选感知历史的价值 |
| pointwise BCE、AUC / GAUC | 先声明正负样本来源。当前只能称采样兴趣判别，不能称真实 CTR；GAUC 要说明单类用户排除比例 |
| pCTR 校准、ESMM、广告多目标 | 单独数据具备曝光、点击、转化等对应标签；聚合 rating_number 不可代替 |
| 搜索 BM25 / 双塔 / cross-encoder | 明确转投搜索且有 query–document 相关性数据；不与推荐主线同时铺开 |
| 生成式推荐、多模态大模型 | 现有闭环完成，有新增研究问题和资源预算 |
| 统一格式化、依赖锁与环境重建 | 保留旧运行快照；验证新源码行为与实际干净安装，不把 observed 包清单称完整跨平台锁 |

两个环境可以保留，服务与 GPU 研究依赖分离本身不是缺陷。真正需要补的是清楚的 extras、安装命令、CUDA/PyTorch 兼容说明和一次不依赖系统包的复建证据。对 tmp 中文件先辨认用途，迁移需长期维护的脚本；无需为公开仓库删除已忽略的个人临时文件。

## 7. 目前可用的项目介绍

> EvoRec 是面向动态商品库的离线推荐研究项目，使用 Amazon Reviews 2023 Video Games 数据。实现统计召回、内容表示和残差 listwise 排序，并通过时间切分、用户留出、验证选型与逐请求审计约束实验。R05 验证规则选中的冷加权排序器在测试集整体 NDCG@10 为 0.009119，相对同候选池 RRF 的观测差值为 +39.5%；冷目标 Top20 命中由 6 增至 26 / 7,088。已定位候选覆盖只有 127 / 7,088 为关键瓶颈，后续重点研究多兴趣召回和排序适配。

讲解时补充：该冷加权结果只有一个种子，尚无显著性结论；普通排序的三种子标准差不属于它。全量源文件扫描过 4,555,500 条交互，但各轮训练使用用户样本，不能写“在 450 万条交互上完成模型训练”。

## 8. GitHub 提交原则

本轮按当前真实内容分组：研究实现与配置、实验报告及博客证据、指导评审及展示修订。研究过程在历史运行归档中记录；补录提交不证明每个提交都对应当时的开发状态，也不修改原运行时间。

公开源代码、配置、汇总指标、报告和图表；原始数据、用户级轨迹、模型文件与虚拟环境不加入 Git。模型路径写在指南里只是本地使用入口，首次 clone 仍需按说明准备数据和训练，不能宣称已提供可直接下载的完整模型发布包。
