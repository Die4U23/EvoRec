## 采纳与修正

| 建议 | 项目采用方式 | 验收重点 |
| --- | --- | --- |
| 显式发布状态机 | 后续持久化 operation_id、状态、目标 bundle、领取代数和每步结果；以数据库持久状态为恢复依据 | 每个实际持久化边界注入崩溃；重试幂等；过期执行者被拒绝 |
| 结构化并发与上下文租约 | 保留已有用例结构；API 取消、远端作业取消、资源释放分别处理 | API 超时后远端仍运行的情况；远端工作停止前不得释放其模型引用 |
| 短事务与乐观校验 | 事务外做不依赖可变状态的准备；事务内核对绑定的会话 epoch、历史版本、活动 bundle、下架版本和接收屏障，再原子落库 | 准备期间反馈或发布发生；同请求重试；提交成功但响应丢失 |
| 分阶段 bundle 校验 | schema → 路径与文件哈希 → 类型和维度兼容 → 受控加载 → 小样本一致性 | 错误映射、缺文件、目录越界、哈希错配、维度错配、内存不足 |
| 共享核心规则 | 保留领域过滤约定，优先做离线/在线适配器的契约一致性测试 | 已见、下架、等时间、重复、并列分数；不为复用而改写已冻结离线源码 |
| 性能与缓存 | 先测阶段耗时、队列和内存，再决定批量及缓存层次 | bundle / exclusion / history 版本进入缓存身份；各 worker 连接池总量与数据库容量匹配 |
| 增量交付 | 先最小持久化闭环，再发布协议和前端；保持独立提交和可失败的验收 | 不把按周估计或经验参数当作已验证工期和性能保证 |

“每步都有回滚路径”需要修正为“每步都有恢复策略”。数据库已提交后，不能仅撤销内存状态就声称事务回滚；必须先对账持久状态，再继续激活或执行带新版本的补偿发布。此方向与现有 ADR-003 一致。

“快速读取可能用脏读”不适用于这里的 PostgreSQL 方案：其 Read Uncommitted 实际按 Read Committed 执行，普通读取只能看到语句开始前已提交的数据。事务外读取可能过时，因此还需要事务内条件核对；并非读快照后就可以直接写入。[PostgreSQL 事务隔离文档](https://www.postgresql.org/docs/current/transaction-iso.html)

asyncio.timeout 取消当前任务并将相应取消转为 TimeoutError；它没有承诺跨进程 GPU 作业自动停止。由此需要在排名适配器中显式传播截止时间、记录远端 job_id，并对仍在执行的工作保留独立租约。取消请求和已停止必须是不同状态。[Python 3.12 协程与超时文档](https://docs.python.org/3.12/library/asyncio-task.html#timeouts)

## 本轮落实

R06 已使用独立协议、代码提交、输入指纹、不可覆盖的运行目录、检查点重载和先选型后测试的阶段门槛。文件卫生检查针对 Git 暂存区，避免被忽略的本地文件掩盖缺失资源；博客与实习材料保持本地。

本轮审计启动曾因工作区切到 main 而找不到 R06 模块；训练本身已经完成且未重跑。恢复时先备份本地材料、切回正确分支并逐文件核对，再从完成的运行记录继续审计。交付检查应同时核对当前分支、运行绑定的提交和源文件快照。

## 后续交付顺序

1. 完成并归档 R06 审计、统计区间、成本报告与未获支持的结果。测试已查看后不根据结果回调当前协议。
2. M11/M12：内存适配器验证闭环后，接 PostgreSQL 的推荐接收与反馈幂等；验收真实并发冲突和提交结果对账。
3. M21/M22：独立 bundle check 工具，再接持久化发布状态机和有界资源切换。旧版本清理要考虑在途引用、回滚窗口和失败诊断，不能只保留固定 N 个就直接删。
4. 完成最小端到端服务后测量瓶颈，再决定动态批量、ANN、C++ 或缓存。前端基于实际稳定接口推进。

以上是后续工程验收安排，不代表服务模块已经实现。原文的固定 pool_size=20、max_overflow=10、分布式缓存层数和两周工期均不作为默认承诺。
