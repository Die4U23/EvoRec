# EvoRec 项目框架与交付路线

版本 0.1｜2026-09-14｜框架设计与工程启动阶段

## 1. 项目目标

围绕“商品持续更新时，如何在给定计算预算下改善推荐”形成可复现实验，并交付能够演示用户反馈、新品入库、策略对比和指标追溯的系统。服务于推荐算法能力展示；结果以实际实验为准。

首版范围遵循现有 PRD：推荐体验、商品生命周期、策略对比、效果看板。交易支付和真实商业流量运营另行立项。

## 2. 三条工作线

| 工作线 | 核心问题 | 交付证据 |
| --- | --- | --- |
| 算法研究 | 基线是否可靠，改动在哪些条件下有效 | 数据协议、基线复现、消融、失败分析与成本记录 |
| 产品实现 | 用户和运营能否完成任务 | 可操作页面、业务接口、持久状态与端到端验证 |
| 工程交付 | 如何重跑、恢复和解释结果 | 环境记录、版本清单、恢复演练、部署及展示说明 |

三条线共享商品 ID、数据协议、版本标识与指标定义。算法实验和产品功能可以分阶段并行，公开展示的结论必须能够关联到真实产物。

## 3. 生命周期与阶段出口

| 阶段 | 必要输入 | 本阶段交付 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 立项与需求 | 项目问题、使用场景 | PRD、范围、验收方向 | 产品行为及边界可解释 |
| 可行性验证 | 数据候选、基线方案、设备信息 | 小规模完整实验、资源记录 | 数据可获取，至少一条算法链路可运行 |
| 总体与详细设计 | PRD、验证结论 | 模块、接口、数据及发布设计 | 关键依赖有契约，异常有处理路径 |
| 迭代实现 | 可执行任务及依赖 | 代码、迁移、自动检查 | 每个增量有完成证据 |
| 系统验收 | 可部署候选版本 | 功能、实验、恢复与性能报告 | 必需场景通过，限制已记录 |
| 发布与展示 | 固定环境、数据和模型 | 启动步骤、演示脚本、版本记录 | 能按说明重放展示，失败能够恢复 |
| 持续迭代 | 运行问题与实验观察 | 新需求、复盘与决策更新 | 明确下一项改动及验证方式 |

阶段出口用于检查事实，不要求个人项目模拟企业审批层级。需求、设计和测试允许在迭代中修订，变更记录说明影响范围。

## 4. 个人项目的责任安排

同一个实现者承担产品、算法、研发和测试职责，但检查问题分别记录：产品检查“行为是否满足需求”，算法检查“实验是否公平”，研发检查“设计是否可实现”，测试检查“证据是否充分”。涉及真实对外发布和外部资源使用时再进行对应决策。

任务只有一个负责人。评审可以使用独立复查或协作者意见，但评审记录只记录实际发生的检查，不填虚构参与人或审批结果。

## 5. 文档之间的关系

PRD 定义“做什么”；选型报告解释“为什么用这些技术”；总体架构定义“如何连接”；数据和接口设计定义“模块之间的约定”；研究协议定义“怎样比较算法”；交付计划将工作映射到需求；验证与发布文档规定“怎样证明完成”。

文档导航见项目 README。框架阶段已经写出的设计仍是可修订草案，其中尚未实现的接口和数据库结构不会作为现有能力展示。

## 6. 变更与风险管理

变更记录至少包含：原因、涉及需求、接口或数据影响、验证方法、对里程碑的影响。外部接口和持久数据有不兼容改动时，提供迁移或版本策略。

| 当前不确定性 | 首次验证动作 | 影响决策 |
| --- | --- | --- |
| GPU、内存与训练预算 | 记录设备并运行最小训练 | 数据规模、模型配置与实验次数 |
| 动态商品时间代理的偏差 | 审查数据字段和时间范围 | 冷物品定义与结果解释范围 |
| 新语义路径生成能力 | 对新增编码做可达性诊断 | 生成式与内容路径的研究假设 |
| 路由收益是否成立 | 与固定策略在相同预算下比较 | 保留或调整路由方法 |
| C++ 是否值得投入 | 分段分析请求耗时 | 是否进入扩展实现 |

研究未得到预期提升时，保留协议与分析，调整结论。功能尚未完成或性能未测量时，在状态页明确说明。
