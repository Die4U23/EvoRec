# EvoRec 架构决策记录

日期：2026-09-15。状态“采用”表示设计已经选定，不等于对应运行组件已完成。完整流程见 [系统架构](../02-architecture.md)。

## ADR-001：单仓库分层，按资源职责分进程

**状态：采用；代码分层已落地，进程拆分待模型接入。**

个人项目要同时推进算法和演示，首先需要稳定接口与可测试规则。采用 domain/application/infrastructure/api 四层，在一个仓库维护；目标运行单元是单业务 API、单推理进程和单后台执行者。API 不随进程数量隐式复制 GPU 模型。

代价是单机和单协调者限制可用性与扩展能力。只有实测出现资源隔离、多人发布或吞吐需求时才考虑增加副本，并先解决全局发布与下架协调。暂不引入 Kubernetes、消息集群或分布式缓存。

## ADR-002：以不可变 bundle 连接研究与服务

**状态：采用；请求版本对象已落地，清单校验与真实加载待实现。**

模型、编码器、码本、物品映射和索引存在兼容关系，需要作为可校验组合发布。每次运行与请求保存 bundle ID；更新写入新目录，旧目录保持不变。

代价是磁盘保留和切换期内存开销。双版本内存不足时明确维护窗口。重新评估条件是数据规模使完整重建成本过高；届时可加入经过等价性检查的增量索引，但继续保留版本与来源证据。

## ADR-003：接收时绑定快照，发布通过屏障对齐

**状态：采用；绑定比对已落地，数据库与运行时协议待实现。**

推荐接收时绑定会话、epoch、历史版本、bundle 和下架版本。发布先构建校验，再关闭接收、提交数据库活动指针、确认运行时、恢复接收。数据库提交之后的故障按已提交状态恢复，必要时执行补偿发布。

该方案把一致性边界放在“请求接收”。下架确认前的在途请求允许旧快照结果；需要全体在途响应立即过滤或多 API 副本时，重新设计协调范围。

## ADR-004：应用用例通过显式接口接入依赖

**状态：已落地。**

接收、排序、结果记录和就绪查询以 Python Protocol 定义，构造函数显式注入。领域与应用层仅依赖标准库及内部对象，HTTP 和模型库细节留在外侧。组装入口统一放在 bootstrap.py。

测试替身用于验证失败路径与执行顺序，默认应用继续报告依赖未配置。实际数据库事务和模型行为另做集成测试。接口数量随真实用例增加，不为每张表提前生成通用仓储层。

## ADR-005：统一过滤规则，保留实际策略与回退原因

**状态：应用层已落地；模型融合与评价实现待接入。**

排序适配器先完成分数融合，应用层检查合法商品、历史和屏蔽状态，去重后稳定排序，候选不足返回实际数量。固定策略改变执行路径必须说明回退原因；adaptive 必须返回解析后的具体策略。

项目默认过滤历史已交互商品，评价协议必须采用同样约定。若研究重复消费任务，先修改任务定义、协议版本和测试，再改变过滤规则。效果提升以公平实验为依据。

## ADR-006：PostgreSQL 承担业务状态与初期任务队列

**状态：采用；现有 SQL 为未执行草案。**

会话反馈、请求结果和任务索引需要事务与幂等约束，先集中在 PostgreSQL。后台按租约领取任务，使用领取代数拒绝过期执行者提交；模型和索引文件保存在受管目录中。

代价是任务领取与业务写入共享数据库资源。只有监控显示争用或任务量确有需要时，再选择独立消息系统。迁移时保留数据库中的业务状态和幂等键，不能把消息投递成功当作业务完成。
